01 / WORKFLOW

預約完成只是開始，
後面還有一整串事。

企業需要的並非一個可以挑日期的表單，還要讓每筆預約都能正確流進營運現場。以下是我們從場地預約專案整理出的標準作業路徑。

01 / 顧客

開啟入口

顧客透過 LINE 進入預約流程，選服務或場地，不用等待專人逐一回覆選項。

02 / 系統

計算可用時段

依營業日、特殊休館、服務長度、前後緩衝及已佔用時段，計算真正可選的時間。

03 / 系統

送出前再檢查

顧客按下確認時再次檢查衝突，避免兩個人同時搶到同一個時間。

04 / 人員

後台審核安排

團隊集中查看待處理與已確認預約，依作業規則核准、拒絕或安排後續工作。

05 / 系統

通知與資料銜接

依部署環境處理通知、提醒與資料匯出，降低前台資訊與原有管理系統之間的落差。

02 / SAAS ARCHITECTURE

一間店的一套流程，
未來可以是多間店的共用產品。

我們正把現場專案中反覆出現的規則做成可配置的模組。管理端建立企業與套用產業範本後，業者再設定自己的服務、場地、營業時段與預約規則。這是 SaaS 化的核心開發方向。

  • 持續維護的共用版本與導入流程
03 / INDUSTRY TEMPLATES

同一個引擎，
長出不同產業的工作方式。

共用的部分盡量不重寫，每個產業真正不同的地方則透過可設定的資源、欄位及規則來處理。

01 / 有專案實作基礎

場館與運動空間

從「場地」出發

一個營業日包含多個場地；使用長度、前後緩衝、休館與臨時時段都會影響可預約空檔。

02 / 產業範本規劃中

講師、顧問與工作室

從「服務／老師」出發

想預約的可能是課程、諮詢或服務人員。後續平台將支援以服務與人員為資源來安排時段。

03 / 有專案實作基礎

活動報名與宮廟行政

從「活動／表單」出發

在預約之外，還要處理報名欄位、費用規則、訂單與文件輸出；相關能力已有另一組專案經驗。

04 / FIELD PROOF

兩個真實場景，
讓產品方向更具體。

我們選擇從流程複雜的現場學習：讓能被驗證的規則先跑通，再談跨公司、跨產業的可複製能力。

01 / 運動場地 LINE 預約

解決『不同入口搶同一個時段』

場館要保留原有系統，也要開放 LINE 新入口。我們以場地時段、緩衝、衝突判斷、審核與匯出為核心，處理前台與後台的連接。

02 / 宮廟補財庫與活動報名

解決『報名資料重複抄寫』

信眾在 LINE 填資料後，行政端仍有付款、訂單、清冊及疏文需求。我們整理成 LIFF 表單、訂單狀態、批次 PDF 與文件版型的流程。

05 / CLAUDE API ROADMAP

我們如何規劃 AI？
讓它幫忙整理，讓規則負責正確。

Claude API 是 ARZ AI 正在評估的工作流程能力。預計先用於閱讀自然語言需求、提取需要補充的資訊，以及產出可供人員檢查的回覆草稿。

01 / AI

語意理解

從『下週二下午想訂場』提出候選日期與時段，不直接改寫預約資料。

02 / AI

表單整理

從詢問文字中整理服務、日期、聯絡需求，缺少資訊時提示補充。

03 / AI

客服草稿

依企業已確認的流程與政策，草擬通知或回覆，交由人員審核。

AI 輔助功能仍在產品規劃與驗證階段；實際可預約性、費用與訂單狀態一律由系統規則及授權人員確認。
